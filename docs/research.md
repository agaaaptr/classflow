## Corrections (verification pass 2026-11-18)

A second parallel research pass (8 topics, ~118 tool calls) verified the claims above. These errors were found; the corrected decisions live in `design.md`.

1. **RLS helper grant** (correcting "Best practices" #3 and the Recommendation): `get_user_role()` must be `revoke ... from public, anon` then `grant execute ... to authenticated` — **not** revoke from `authenticated`. Policy expressions run as the caller, so revoking from `authenticated` makes every RLS query fail. (The idempotent-earnings section already states the right sequence; the two contradicted.)
2. **`ON CONFLICT` inference** (correcting idempotent-earnings #2): a plain `UNIQUE` constraint is inferable by `ON CONFLICT (cols)`; `CREATE UNIQUE INDEX` is needed only for partial/expression indexes. Use a normal constraint.
3. **Integer overflow unit:** `integer` caps at 2,147,483,647 ≈ **Rp2,15 miliar**, not "Rp2,1 juta".
4. **IDR scale:** ISO 4217 lists IDR exponent 2 (sen). Whole-rupiah scale-0 is a documented simplification (sen obsolete; CLDR cash digits 0), not the ISO exponent.
5. **`auth.identities` seed:** write `provider_id` = the user UUID; do not insert `id` (auto-PK) or `email` (GENERATED, error 428C9). Put email in `identity_data` via `jsonb_build_object('sub', id, 'email', email)`.
6. **Money expression:** `round(rate × menit / 60)` integer-divides first and then `round()` is a no-op. Use `round(rate_rp::numeric * minutes / 60.0)::bigint` (70 min @ Rp100k = Rp116.667, not 116.666).
7. **Next.js 16:** the third Supabase file is `proxy.ts` (export `proxy()`), not `middleware.ts`; `@supabase/ssr` 0.12.x uses request/response cookies and `getAll`/`setAll`; keys are now `publishable`/`secret`.
8. **2026 Data-API GRANT change (precise dates):** opt-in 2026-04-28, default for new projects 2026-05-30, enforced for all 2026-10-30.

## Supabase multi-role authorization (admin / tutor / student) with Row Level Security

**Summary:** The current (2024-2025) Supabase guidance is consistent: keep the role in a database table as the source of truth (a `profiles` or `user_roles` table with a `role` column), and check that role inside RLS via a `SECURITY DEFINER` helper function that calls `auth.uid()`. Never authorize on `user_metadata` (it is user-editable via `supabase.auth.updateUser()` and enables self-promotion to admin, flagged by Supabase lint 0015 / CWE-269). `app_metadata` is server-only and JWT-visible but role changes lag until token refresh, so it is a mirror, not the source of truth. The official "Custom Claims & RBAC" guide recommends: (1) a `user_roles` table as source of truth, (2) a Custom Access Token Auth Hook that reads it and injects a `user_role` claim into the JWT, (3) an `authorize()` helper reading `auth.jwt() ->> 'user_role'`, and (4) per-role RLS policies. A DB-table helper (`get_user_role()`) is the authoritative, instant-reflect pattern and also avoids the recursive-policy cycle (a SELECT policy on `profiles` querying `profiles`). For this 3-role app the concrete pattern is: `profiles` table with a `role` column (CHECK constraint `admin|tutor|student`), a `SECURITY DEFINER get_user_role()` helper with `set search_path = ''`, and per-role RLS policies that compare `get_user_role()` and `auth.uid()` — plus optional JWT mirroring via the access-token hook for joinless checks.

### Best practices

1. **Store the role as the source of truth in a `profiles` (or dedicated `user_roles`) table with a `role` column constrained to 'admin'|'tutor'|'student', and look it up in RLS via a helper function. Do NOT treat `user_metadata`/`raw_user_meta_data` as authoritative.** — The client controls `user_metadata` at sign-up and can rewrite it with `auth.updateUser({ data: { role: 'admin' } })`, so authorizing on it is a privilege-escalation hole (Supabase lint 0015, CWE-269). A DB table whose writes only the server/service_role can perform is the trusted source.
   - https://supabase.com/docs/guides/api/custom-claims-and-role-based-access-control-rbac
2. **Check the role inside RLS with a `SECURITY DEFINER` helper function, e.g. `public.get_user_role()` returning the role for `auth.uid()` (or `is_admin()` / `has_role('tutor')`). Always check `auth.uid()` inside the function body.** — SECURITY DEFINER runs with the owner's privileges so it can read the role table even when the caller's RLS would block it, and it centralizes the check so every policy uses the same logic. Checking `auth.uid()` inside is mandatory because the function bypasses RLS on the tables it touches.
   - https://github.com/BrewHubPHL/supabase-specialist/blob/master/patterns/rls-policies.md
3. **Harden the SECURITY DEFINER helper: `set search_path = ''` and schema-qualify table names, put it in a non-exposed schema (e.g. `private`), and `revoke execute ... from public, anon, authenticated`.** — An exposed SECURITY DEFINER function is callable through the Data API with the owner's privileges and is vulnerable to search-path/function-hijacking attacks. `search_path = ''` forces explicit schema qualification; revoking execute keeps clients from invoking it directly.
   - https://github.com/pproenca/dot-skills/blob/HEAD/skills/.experimental/opinionated-nextjs-patterns/references/auth-use-sql-policy-helpers.md
4. **Write one policy per role using `auth.uid()`. Students see only their own rows; tutors see rows where they are assigned (`tutor_id = auth.uid()`); admins see everything via a role check like `get_user_role() = 'admin'`. Prefer `TO authenticated` and include both `USING` and `WITH CHECK`.** — Separate per-role policies keep the intent explicit and match the app's rules (students see only paid classes, tutors only assigned classes, admin approves logbooks). `WITH CHECK` guards INSERT/UPDATE in addition to `USING` for SELECT, and `TO authenticated` avoids anon evaluation.
   - https://supabase.com/docs/guides/database/postgres/row-level-security
5. **Optionally mirror the role into the JWT with a Custom Access Token Auth Hook: read `public.user_roles`/`profiles` in the hook and `jsonb_set` a `user_role` claim, then read it in RLS via `auth.jwt() ->> 'user_role'`. Grant the hook function to `supabase_auth_admin` and revoke from `public`/`anon`/`authenticated`.** — This is the official 2024-2025 pattern and gives fast, joinless RLS checks. The JWT claim is only a cache/mirror because claims don't update until the token refreshes, so the DB table stays the source of truth.
   - https://supabase.com/docs/guides/auth/auth-hooks/custom-access-token-hook
6. **Prevent role self-escalation: never let users UPDATE the `role` column. Use a dedicated `user_roles` table with no client INSERT/UPDATE policies, or use column-level grants (`revoke update on profiles from authenticated; grant update (full_name, avatar_url) on profiles to authenticated;`).** — RLS protects rows, not columns: an `auth.uid() = id` update policy would otherwise let a user run `update profiles set role = 'admin' where id = auth.uid()`. Restricting the column or table writes closes this.
   - https://thefrontkit.com/blogs/supabase-row-level-security
7. **Wrap `auth.uid()` in a subquery, `(select auth.uid())`, and index the columns referenced in policy predicates (`user_id`, `role`, `class_id`, `tutor_id`).** — RLS runs the predicate once per row; subquery-wrapping lets PostgreSQL evaluate `auth.uid()` once and cache it, and indexes keep per-role scans fast as rows grow.
   - https://github.com/BrewHubPHL/supabase-specialist/blob/master/patterns/rls-policies.md
8. **Enforce the role at three layers: client-side UI guard, server-side route/server-action check via `getUser()` (not `getSession()`), and DB RLS as the final backstop.** — Defense in depth: the DB is the only non-bypassable layer; `getUser()` re-validates the JWT against the auth server, unlike `getSession()` which trusts the client-supplied session.
   - https://rapidevelopers.com/supabase-tutorial/how-to-protect-admin-routes-with-supabase

### Pitfalls

- Authorizing on user_metadata/raw_user_meta_data: any user can set data.role='admin' client-side via supabase.auth.updateUser() — privilege escalation (Supabase lint 0015, CWE-269).
- A writable role column: an update policy like auth.uid() = id on profiles lets users set their own role='admin'; RLS protects rows, not columns. Revoke update on the role column or use a separate user_roles table.
- Custom claims are not in the JWT unless explicitly set: the access-token hook must be registered (config.toml [auth.hook.custom_access_token] locally) and granted to supabase_auth_admin; otherwise auth.jwt() ->> 'user_role' is null.
- JWT claim staleness: role changes reflected in app_metadata or a token hook do not take effect until the token/session refreshes, so JWT should never be the only role store.
- Exposed SECURITY DEFINER function: without search_path = '' and revoke execute from public/anon/authenticated, clients can call it through the Data API with owner privileges, and it is open to search-path injection.
- SECURITY DEFINER bypasses RLS on the tables it reads, so the function must always scope by auth.uid() or it leaks other users' data.
- Recursive policy cycles: a SELECT policy on profiles that itself does SELECT ... FROM profiles to check role can recurse; use a SECURITY DEFINER helper (not subject to the same RLS) to break the cycle.
- Trusting getSession() server-side instead of getUser(): getSession() trusts the client-supplied session and can be spoofed; use getUser() for role/route enforcement.
- Leaking the service_role key to the browser: it bypasses RLS entirely; keep it in server-only env vars.
- The Supabase SQL editor runs with service_role/postgres and bypasses RLS, so policies must be tested by impersonating users (set local role authenticated / pgTAP), not by running queries in the editor.

### Recommendation

For this Group Class Enrollment & Billing app, use the DB-table-as-source-of-truth pattern (simplest correct option, no JWT required to start):

1. `public.profiles` table: `id uuid primary key references auth.users(id) on delete cascade`, `full_name text`, and `role public.app_role not null default 'student'` where `app_role` is a Postgres enum or a TEXT with `CHECK (role IN ('admin','tutor','student'))`. Seed the first admin server-side with the service_role key.

2. Lock the role column: users must not be able to self-promote. Either (a) put role in a separate `public.user_roles` table with no INSERT/UPDATE policies for clients, or (b) keep it in `profiles` but `revoke update on profiles from authenticated` and re-grant only the non-role columns. Pick (b) for fewer tables, (a) if you expect role grants to be a distinct admin flow.

3. Add a hardened helper in a private schema:
```sql
create function private.get_user_role() returns public.app_role
language sql stable security definer set search_path = ''
as $$ select role from public.profiles where id = auth.uid() $$;
revoke execute on function private.get_user_role() from public, anon, authenticated;
```

4. Write per-role RLS policies that reference `private.get_user_role()`:
- students: `using (student_id = auth.uid())` / `get_user_role() = 'student'`
- tutors: `using (tutor_id = auth.uid())` for assigned classes/logbooks
- admin: `using (get_user_role() = 'admin')` with both USING and WITH CHECK
- logbooks: hide unapproved from students (e.g. `using (get_user_role() in ('admin','tutor') or approved = true)`).

5. Optional, later: add the official Custom Access Token Auth Hook to mirror `role` into a `user_role` JWT claim and switch hot paths to `auth.jwt() ->> 'user_role'` for joinless checks — but keep `get_user_role()` as the authoritative check, because JWT claims lag until refresh.

Do not read role from `user_metadata`/`raw_user_meta_data` anywhere. Keep the `service_role` key server-only (never in the browser).

## Supabase PostgreSQL schema, migrations, and seed SQL best practices

**Summary:** For a reproducible fresh clone, structure and seed data live in two places: versioned schema lives in `supabase/migrations/` as timestamped `<YYYYMMDDHHMMSS>_description.sql` files (created with `supabase migration new`), and data lives in `supabase/seed.sql` (or multiple ordered files via `config.toml` `[db.seed].sql_paths`). `supabase db reset` drops and recreates the local DB by replaying all migrations in filename order, then runs the seed — this is the standard check that a fresh clone works; commit `supabase/config.toml` too. Seed files must be data-only and idempotent (`ON CONFLICT DO NOTHING`); never put schema statements in seeds and never put data INSERTs in migrations. Seeded auth users with known passwords are created by hashing with `crypt(password, gen_salt('bf'))` (pgcrypto) and inserting into BOTH `auth.users` and `auth.identities`, with `email_confirmed_at = now()`, empty-string (not NULL) token columns, and `raw_app_meta_data` containing `"provider":"email"`. Hard business invariants belong in the database as the last line of defense: UNIQUE/partial-unique indexes for uniqueness, EXCLUDE USING gist for non-overlapping lessons, triggers (with row locks) for cross-row limits like capacity, and BEFORE UPDATE triggers + RLS for read-only-approved-logbook. Application code layers on top for UX and friendly error mapping, never as the only guard. Note the 2026 Supabase default change: new projects do not auto-grant Data API access to `public` tables, so migrations must `GRANT ... TO authenticated` in addition to enabling RLS.

### Best practices

1. **Keep schema, RLS, triggers, functions, and indexes in `supabase/migrations/*.sql` with timestamped names; keep seed files data-only and idempotent. Schema changes go in migrations, data INSERT/UPDATE goes in seed.** — Migrations replay in filename order to build a clean schema; seeds run only on `db reset`/fresh DB. Mixing them makes a fresh clone non-reproducible.
   - https://supabase.com/docs/guides/deployment/database-migrations
2. **Make every seed insert idempotent with `ON CONFLICT DO NOTHING` (or `DO UPDATE`) and use predictable UUID/keys; never `TRUNCATE CASCADE` reference data in seeds.** — `db reset` is safe but seeds are also re-run in some workflows; idempotency prevents duplicate rows and surprises.
   - https://supabase.com/docs/guides/local-development/seeding-your-database
3. **Verify a fresh clone with `supabase db reset` (replays migrations then seed) and commit `supabase/config.toml`; test migrations with pgTAP under `supabase/tests/`.** — `db reset` is the canonical reproducibility check; `config.toml` and migration files are the only state that must travel between machines.
   - https://www.hesham.us/supabase-field-manual/supabase-local-stack-supabase-start-link-push-gen-types
4. **Seed auth users with `crypt(password, gen_salt('bf'))` and insert into both `auth.users` and `auth.identities`; set `email_confirmed_at = now()`, empty-string token columns, and `raw_app_meta_data = '{"provider":"email","providers":["email"]}'`.** — Supabase's GoTrue hashes with its own salt, so off-the-shelf bcrypt hashes fail with 'Invalid credentials'; since Nov 2023 `auth.identities.provider_id` is NOT NULL and sign-in fails without the identity row; NULL token columns throw 'converting NULL to string is unsupported'.
   - https://dev.to/mikh-shytsko/supabase-db-seed-seedsql-configtoml-authusers-5e4k
5. **For no-overlapping lessons, use `CREATE EXTENSION btree_gist;` then `EXCLUDE USING gist (tutor_id WITH =, tstzrange(start_at, end_at) WITH &&)` (or `during &&` on a tstzrange column).** — An exclusion constraint is concurrency-safe where app 'check-then-insert' races; `tstzrange` defaults to `[)` so back-to-back lessons at [09:00,10:00) and [10:00,11:00) correctly do not conflict.
   - https://www.cybertec-postgresql.com/en/postgresql-exclusion-constraints-beyond-unique/
6. **Enforce capacity limit with a `BEFORE INSERT` trigger that first locks the class row (`SELECT ... FOR UPDATE`), then counts enrollments and `RAISE EXCEPTION` if `count >= capacity`. Do NOT use a CHECK constraint or a function-wrapped subquery.** — PostgreSQL CHECK cannot contain subqueries and can only see the current row; a function-wrapped subquery silently goes stale when other rows change and breaks pg_dump. A trigger with a row lock is the correct, race-safe mechanism.
   - https://stackoverflow.com/questions/62429478/check-count-in-postgres
7. **Enforce one logbook per class per month with a UNIQUE index on `(class_id, tutor_id, month)` where `month` is a stored column (e.g. `date_trunc('month', ...)` or `YYYY-MM`).** — A composite UNIQUE index is the simplest, concurrency-safe way to express 'no duplicate per class/tutor/month'; it also gives a fast lookup path.
   - https://github.com/pproenca/dot-skills/blob/master/skills/.experimental/relational-data-modeling/references/cons-check-is-single-row.md
8. **Make an approved logbook read-only with a `BEFORE UPDATE` trigger: `IF OLD.status = 'approved' THEN RAISE EXCEPTION ...; END IF;` (and optionally guard specific columns), combined with RLS so students cannot read unapproved rows.** — A guard trigger blocks mutation at the source regardless of which client sends it; column-level GRANT or RLS alone leaves the server-side path open. Restrict only the client-editable columns so trusted maintenance paths are not blocked.
   - https://stackoverflow.com/feeds/question/15411735
9. **In migrations, both `GRANT SELECT/INSERT/UPDATE/DELETE ON public.<table> TO authenticated;` (and `anon` only for public reads) AND `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;` with policies using `(select auth.uid())` and explicit `TO authenticated`.** — Since May 2026 new Supabase projects do not auto-grant Data API access to public tables — without GRANT the frontend gets empty results regardless of RLS; without policies there is no row filtering. `(select auth.uid())` is evaluated once for performance.
   - https://supabase.com/docs/guides/database/postgres/row-level-security
10. **Layer app code on top of DB constraints only for UX: pre-validate and map Postgres error codes (`23505` unique_violation, `23P01` exclusion_violation, `P0001` raised exceptions) to friendly messages.** — DB constraints are the non-bypassable last line of defense; the app layer gives fast feedback and readable errors but must never be the only guard.
   - https://dev.to/appfirstaid/supabase-permission-denied-for-table-42501-on-a-new-table-why-it-happens-and-the-safe-fix-21dn

### Pitfalls

- Editing an already-applied migration file: `db push` compares file names against the applied list, so edits to applied files are silently skipped and history desyncs. Always add a new migration.
- Trying to enforce capacity with a CHECK constraint: `CHECK` cannot contain subqueries (`cannot use subquery in check constraint`), and the function-wrapped-subquery workaround goes stale when other rows change and breaks pg_dump/VALIDATE CONSTRAINT.
- Seeding `auth.users` without a matching `auth.identities` row, or without empty-string token columns: sign-in fails (identities required since 2022 GoTrue change) and NULL tokens throw 'converting NULL to string is unsupported'.
- Using a bcrypt hash generated outside Postgres: Supabase/GoTrue salts its own hashes, so `crypt(password, gen_salt('bf'))` must be run in SQL or the admin API used instead.
- Trigger that counts rows without locking the parent (class) row: two concurrent inserts can both pass the count and exceed capacity. Lock the class row first.
- Forgetting to `GRANT ... TO authenticated` on new public tables in 2026+ Supabase projects: RLS alone yields empty/404 responses from the Data API.
- Putting `TRUNCATE CASCADE` or non-idempotent destructive statements in seed.sql, and committing production password hashes/PII into seed files.

### Recommendation

Put all four invariants in the database (with app code as a UX layer only): (1) Unique enrollment -> composite `UNIQUE (class_id, student_id)`, or a partial unique index `WHERE status <> 'dropped'` if enrollments are soft-deleted; (2) capacity limit -> a `BEFORE INSERT/UPDATE` trigger on the enrollment table that does `SELECT ... FOR UPDATE` on the class row, counts enrollments, and raises if `count >= class.capacity` — do not use CHECK (no subqueries) or a function-wrapped subquery; (3) one logbook per class per month -> `UNIQUE (class_id, tutor_id, month)` where `month` is a stored column (`date_trunc('month', ...)` or `YYYY-MM`); (4) approved-logbook read-only -> a `BEFORE UPDATE` trigger raising when `OLD.status = 'approved'`, plus RLS `FOR SELECT`/`FOR UPDATE` policies so students cannot read unapproved logbooks and tutors only their own. In every migration, enable RLS AND `GRANT ... TO authenticated` (new Supabase projects do not auto-grant Data API access). Seed known-password users via `crypt(password, gen_salt('bf'))` into both `auth.users` and `auth.identities`. Verify everything with `supabase db reset`; map Postgres error codes (23505, 23P01, P0001) in the app for friendly messages.

## Storing money in PostgreSQL (Indonesian Rupiah) and invoice/payment state modeling

**Summary:** Research consensus is unambiguous on all three sub-questions. (1) Money type: never use float/real/double (binary base-2 cannot represent decimal values exactly; errors accumulate in sums). Never use PostgreSQL's built-in `money` type (locale-dependent, no fractional cents). The choice is between integer minor-units and `numeric`. For IDR specifically, because the `sen` subunit is obsolete and rupiah has no decimal in common use, the recommended type is `bigint` storing whole rupiah (scale exponent 0): it is exact, fast, and summable. Xendit's own benchmark found NUMERIC aggregation ~60% slower than integer. Use `bigint`, not `integer`, because `integer` caps at ~2.147 billion (~Rp2.1M), trivially exceeded by IDR amounts. (2) Invoice status: model it as a single explicit `status` column (a small state machine: draft -> unpaid -> paid, plus cancelled), never as a pile of booleans (`is_paid`, `is_cancelled`) which admit invalid states. Store the human-chosen states and record `paid_at`; deriving payment state from payment rows is an optional refinement, not needed for a simulated no-gateway flow. (3) Simulated payment flow: admin manually confirms payment; status transitions pending -> paid, with optional payment-proof reference and an audit trail. No gateway, no transaction IDs, no automation.

### Best practices

1. **Store money as `bigint` in whole Rupiah units (no decimal). IDR's minor unit (sen) is obsolete and unused, so the scale exponent is 0: Rp1.500.000 is stored as integer 1500000.** — Exact integer arithmetic, fast aggregation, no floating-point drift, and no decimal scaling needed because rupiah has no decimal subunit in common use.
   - https://www.matthewswong.com/en/blog/integer-rupiah-vs-numeric-decimal-postgres-erp/
2. **Use `bigint`, not `integer`, for the money column. `integer` overflows at 2,147,483,647 (~Rp2.1 juta); `bigint` caps at ~9.2 quintillion, safe for IDR.** — IDR amounts are large nominal numbers; plain `integer` overflows trivially and turns into a 500 error.
   - https://candraoctavianr.com/insights/handling-high-cardinality-currency-precision-in-distributed-billing-systems
3. **Never use `float`/`real`/`double precision` for money. Example failure: 0.1 + 0.2 = 0.30000000000000004 in float, exact 0.3 in numeric/integer.** — Binary floating point cannot represent most decimal values exactly; tiny errors accumulate in aggregate billing and tutor-earnings sums.
   - https://www.crunchydata.com/blog/working-with-money-in-postgres
4. **Avoid PostgreSQL's native `money` type.** — It is tied to the database locale (currency symbol/formatting) and cannot represent fractional cents; useful only for display casting.
   - https://www.rockdata.net/blog/working-with-money/
5. **If you ever need decimals (e.g. multi-currency or fractional rates), use `numeric(p, s)` with explicit precision/scale — e.g. `numeric(12,2)` — not float. Integer minor-units remain the preferred default for single-currency IDR.** — `numeric` is arbitrary-precision and exact, at the cost of ~60% slower aggregation and ~10 bytes/row.
   - https://blog.xendit.engineer/benchmarking-pg-numeric-integer-9c593d7af67e
6. **Model invoice status as a single `status` column with a small state machine: `draft` -> `unpaid` (sent/pending) -> `paid`, plus `cancelled`. Enforce it with a Postgres `CHECK (status IN ('draft','unpaid','paid','cancelled'))` and a TypeScript enum.** — A single status column makes impossible states architecturally impossible and yields clean indexable `WHERE status = 'paid'` queries. Booleans (`is_paid`, `is_cancelled`) admit invalid combinations and scatter conditionals.
   - https://dev.to/kyisaiah47/getting-paid-is-a-state-machine-problem-142j
7. **Record a `paid_at timestamptz` (and optionally `cancelled_at`) alongside `status`; keep money line items read-only once status leaves `draft`.** — Transition metadata supports audit and reporting, and freezing amounts at transition prevents retroactive edits.
   - https://www.velinexlabs.com/blog/the-case-for-boring-state-machines-in-financial-workflows
8. **For the simulated no-gateway payment flow, keep it to: an admin 'mark as paid' action that flips `status` from `unpaid`/`pending` to `paid` and sets `paid_at`, plus an optional `payment_proof` reference column (URL/reference string). No gateway transaction IDs.** — Manual confirmation is the standard no-gateway pattern; 'nothing is verified automatically', the admin confirms, then downstream actions (e.g. enrollment) are unlocked.
   - https://blog.hamzaelmansouri.online/blog/building-a-store-without-a-payment-gateway-manual-checkout-with-nextjs-and-supabase
9. **Keep a currency code column (`currency char(3) default 'IDR'`) even if only IDR is used now.** — A bare integer amount is ambiguous (whole units vs cents) the moment a second currency shares the column; a currency code removes that ambiguity cheaply.
   - https://docs.stripe.com/currencies
10. **At the API boundary, serialize big integer amounts as JSON strings (or numbers with a documented unit) and convert `SUM()` results explicitly — Postgres `sum()` over a `bigint` returns `numeric`/`bigint` and JavaScript `JSON.stringify(BigInt)` throws.** — Avoids BigInt serialization crashes and the off-by-100x confusion between whole rupiah and sen.
   - https://www.fullstacknotes.org/blog/postgresql-dari-nol-hingga-mahir-2-tabel-tipe-data-constraint

### Pitfalls

- Using `float`/`double precision` for money: binary rounding errors accumulate across logbooks and tutor-earnings sums and cause incorrect totals.
- Using PostgreSQL's `money` type: locale-dependent formatting and inability to represent fractional cents.
- Using `integer` (32-bit) for IDR amounts: overflows at ~Rp2.1 juta; use `bigint`.
- Modeling invoice state as booleans (`is_paid`, `is_cancelled`): permits invalid states and scatters transition logic across the codebase.
- Forgetting `paid_at`/transition timestamps: makes audit and 'approved once' idempotency harder to verify.
- Over-engineering the state machine: adding `sent`/`viewed`/`overdue`/`dispute` states not required by the brief — the take-home needs only draft/unpaid/paid (plus cancelled).
- Storing the decimal subunit inconsistently: IDR's official ISO 4217 exponent is 2 (sen), but sen is obsolete — mixing 'whole rupiah' and 'sen' representations causes off-by-100 errors; pick whole-rupiah `bigint` and document it.
- Not adding a `CHECK (amount >= 0)` constraint: negative amounts should be rejected at the DB, not only in app code.
- Calling a payment gateway when the brief specifies no gateway: the requirement is a simulated/manual-confirmation flow, no transaction IDs, no automation.

### Recommendation

Concrete schema for this take-home. Money: `amount_rp bigint not null check (amount_rp >= 0)` storing whole Rupiah (no decimal; e.g. Rp1.500.000 -> 1500000). This applies to package price, class student/tutor rates, tutor earnings, and any invoice total. Invoice/status: a single `status text not null default 'draft' check (status in ('draft','unpaid','paid','cancelled'))` column on the invoice/enrollment-payment table, plus `paid_at timestamptz` (null until paid) and an optional `payment_proof text` reference. Simulated payment flow: admin action flips `status` from `unpaid` to `paid`, sets `paid_at = now()`, then (per the app's rules) unlocks enrollment/capacity. Do not use float, do not use the `money` type, do not use booleans for status, and use `bigint` rather than `integer`. Keep a `currency char(3) default 'IDR'` column for future-proofing. Serialize bigint amounts as strings at the API boundary to avoid BigInt JSON crashes.

## scheduling-no-overlap-timezone-postgresql

**Summary:** PostgreSQL enforces a tutor's no-overlapping-lessons rule at the database level with an EXCLUDE constraint backed by a GiST index over tstzrange, which is race-free under concurrency (unlike app-level check-then-insert). Lesson start/end are stored as `timestamptz` columns holding UTC absolute instants; `timestamptz` renders per the session TimeZone but never loses the instant, and is rendered in WIB (UTC+7) via the IANA zone 'Asia/Jakarta'. End-after-start is a simple CHECK constraint, and the default half-open `[)` bound semantics mean back-to-back lessons do not falsely collide. Requires the `btree_gist` extension to combine scalar `=` with the range `&&` operator in the GiST index.

### Best practices

1. **Store lesson start/end as two `timestamptz NOT NULL` columns holding UTC values; never use `timestamp without time zone` for real lesson times.** — `timestamptz` stores a single absolute instant (UTC internally) and is correct across timezones and DST transitions; `timestamp` stores only a wall-clock value and loses the instant, a common anti-pattern inherited from timezone-less databases. The bare `WIB` abbreviation may not even be recognized by Postgres.
   - https://stackoverflow.com/questions/79838897/postgresql-should-i-store-timestamps-as-unix-epoch-or-timestamptz/79838914
2. **Create the exclusion constraint as `EXCLUDE USING gist (tutor_id WITH =, tstzrange(starts_at, ends_at) WITH &&)` after `CREATE EXTENSION IF NOT EXISTS btree_gist;`.** — This is the canonical non-overlap pattern: two rows conflict only when the tutor is equal AND the ranges overlap. The GiST index is created automatically and also serves availability/overlap queries. `btree_gist` adds GiST operator-class support for the scalar `=` on tutor_id. Conflicting inserts raise SQLSTATE 23P01 (exclusion_violation), which the API can map to a 409.
   - https://dev.to/ahmed_farouk_9cf00a49e7a5/how-i-stop-double-bookings-in-a-booking-app-let-postgres-refuse-them-49kg
3. **Use half-open `[)` range bounds (inclusive start, exclusive end) — the default of the two-argument `tstzrange(start, end)` constructor.** — With `[)`, a lesson ending at 10:00 and another starting at 10:00 do NOT overlap. Using `[]` (inclusive both ends) makes every back-to-back booking a false conflict — described as the usual first bug report after adopting exclusion constraints.
   - https://www.red-gate.com/simple-talk/databases/postgresql/overlapping-ranges-in-subsets-in-postgresql/
4. **Add `CONSTRAINT lessons_ends_after_starts CHECK (ends_at > starts_at)` with `NOT NULL` on both timestamp columns.** — PostgreSQL CHECK constraints pass when the expression is TRUE or NULL and only fail on FALSE, so a NULL end/start would slip through; NOT NULL closes that hole. The CHECK enforces end-after-start per row; only the EXCLUDE constraint catches cross-row overlap.
   - https://docs.cloud.google.com/spanner/docs/check-constraint/how-to
5. **Keep storage in UTC and render in WIB at the UI/API layer using the named IANA zone 'Asia/Jakarta', not the numeric offset '+07'. In SQL use `SET TIME ZONE 'Asia/Jakarta'` or `starts_at AT TIME ZONE 'Asia/Jakarta'`.** — Named IANA zones apply historical rule changes; numeric offsets do not. `AT TIME ZONE 'Asia/Jakarta'` returns a `timestamp` (wall clock, without tz) shifted to WIB. In a Next.js client, `Intl.DateTimeFormat('id-ID', { timeZone: 'Asia/Jakarta' })` renders UTC instants in WIB without touching the stored value.
   - https://ngulikdata.com/blog/sql-timezone

### Pitfalls

- Using `timestamp without time zone` for lesson times: loses the absolute instant and breaks cross-timezone/DST correctness; the search results call this a common inherited anti-pattern.
- Using `[]` inclusive bounds on both ends: back-to-back lessons falsely collide under the exclusion constraint; prefer the default half-open `[)`.
- Forgetting `CREATE EXTENSION btree_gist`: the scalar `=` on tutor_id has no GiST operator class and the EXCLUDE constraint fails to create on a fresh database.
- Relying on app-level check-then-insert instead of the DB exclusion constraint: race conditions under concurrent requests produce double bookings; only the constraint is race-free (23P01).
- Missing `NOT NULL` on the timestamp columns: the CHECK `ends_at > starts_at` evaluates to NULL (not FALSE) when either side is NULL, so CHECK passes and bad rows are admitted.
- Building the range from `timestamp` (without tz) columns inside the EXCLUDE expression: the GiST index expression is non-IMMUTABLE (depends on session TimeZone) and errors with 'functions in index expression must be marked IMMUTABLE'; with `timestamptz` inputs `tstzrange(timestamptz, timestamptz)` is IMMUTABLE and works.
- Grouping daily reports by UTC date: day boundaries shift by 7 hours vs WIB; convert to 'Asia/Jakarta' first, then cast to `date`.
- Using the literal 'WIB' or '+07' as the time zone: 'WIB' may be absent from pg_timezone_abbrevs (invalid input syntax), and numeric offsets ignore historical timezone rules — use IANA name 'Asia/Jakarta'.

### Recommendation

Use two `timestamptz` columns (UTC absolute instants) and enforce no-overlap per tutor with a GiST exclusion constraint, plus a per-row CHECK. Concrete migration:

```sql
create extension if not exists btree_gist;

create table lessons (
  id          uuid primary key default gen_random_uuid(),
  class_id    uuid not null references classes(id) on delete cascade,
  tutor_id    uuid not null references profiles(id),
  starts_at   timestamptz not null,  -- UTC instant
  ends_at     timestamptz not null,  -- UTC instant

  constraint lessons_ends_after_starts
    check (ends_at > starts_at),

  constraint lessons_tutor_no_overlap
    exclude using gist (
      tutor_id with =,
      tstzrange(starts_at, ends_at) with &&
    )
);
```

Notes: the two-argument `tstzrange(starts_at, ends_at)` defaults to half-open `[)` so back-to-back lessons do not conflict; the inputs are `timestamptz`, so the index expression is IMMUTABLE (no "must be marked IMMUTABLE" error). If a tutor may also be double-booked across classes, add another equality key (e.g. `class_id with =`) to the same constraint — but per the requirement, `tutor_id with =` alone prevents any two overlapping lessons for one tutor. Render WIB in the client with `Intl.DateTimeFormat('id-ID', { timeZone: 'Asia/Jakarta', ... })` (or `SET TIME ZONE 'Asia/Jakarta'` / `AT TIME ZONE 'Asia/Jakarta'` in SQL); store nothing but UTC. Map SQLSTATE 23P01 to an HTTP 409 conflict response on insert.

## Next.js App Router + Supabase auth/data access (@supabase/ssr)

**Summary:** The idiomatic 2024-2025 setup uses @supabase/ssr with three typed clients plus a middleware/proxy. The @supabase/auth-helpers packages are deprecated; install @supabase/supabase-js and @supabase/ssr. (1) lib/supabase/client.ts uses createBrowserClient as a singleton for Client Components; (2) lib/supabase/server.ts uses createServerClient with cookies() from next/headers, one client per request, for Server Components, Server Actions and Route Handlers; (3) middleware.ts (Next.js 15 and earlier; proxy.ts in Next.js 16) refreshes the auth token because Server Components cannot write cookies. Auth guidance (2025): use getClaims() or getUser() for authorization — getClaims verifies the JWT signature locally, getUser hits the Auth server to catch revoked/banned sessions; never trust getSession() in server code because it just reads the forgeable cookie. Fetch data in Server Components, do mutations in Server Actions, and use Route Handlers only for webhooks/external callbacks. The real security boundary is PostgreSQL RLS, not UI hiding or middleware redirects: RLS is off by default on new Supabase tables, and every Server Action/Route Handler must independently re-verify auth and role with getUser(), since middleware does not protect direct POSTs to server actions.

### Best practices

1. **Install @supabase/ssr (with @supabase/supabase-js); the @supabase/auth-helpers-* packages are deprecated. Use NEXT_PUBLIC_SUPABASE_URL and the anon/publishable key in .env.local, never the service_role key on the client.** — 
   - https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs
2. **Create one client file per type: lib/supabase/client.ts (createBrowserClient singleton for Client Components), lib/supabase/server.ts (createServerClient with cookies() from next/headers for Server Components, Server Actions and Route Handlers), and a middleware.ts/proxy.ts that refreshes the session.** — 
   - https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs&queryGroups=environment&environment=route-handler
3. **In middleware/proxy, call supabase.auth.getClaims()/getUser() to trigger token refresh, write cookies via the cookies.setAll callback, and always return the supabaseResponse object (or copy its cookies and cache headers onto any new response) so refreshed tokens are not lost.** — 
   - https://supabase.com/docs/guides/auth/server-side/creating-a-client
4. **Use getUser() (or getClaims()) for authorization and page protection; never trust getSession() in server code — it reads the session from the cookie without revalidating and the cookie can be forged.** — 
   - https://supabase.com/docs/guides/auth/server-side/advanced-guide
5. **Fetch data directly in async Server Components and pass minimal serializable props to Client Components; use Server Actions for mutations (validate with Zod, return typed {success, data|error}, call revalidatePath/revalidateTag after writes); use Route Handlers only for webhooks/external callbacks.** — 
   - https://supabase.com/docs/guides/auth/server-side/creating-a-client
6. **Treat RLS as the actual security boundary. Enable RLS on every exposed table, keep it on, and encode per-role access in policies keyed to auth.uid()/JWT claims — not just hidden UI or middleware redirects.** — 
   - https://supabase.com/docs/guides/database/postgres/row-level-security
7. **Re-verify auth AND role inside every Server Action and Route Handler with supabase.auth.getUser(); return 401 (unauthenticated) / 403 (forbidden). Middleware protects navigation only and does not guard direct POSTs to server actions.** — 
   - https://aevral.com/guides/nextjs-supabase-authorization-before-launch
8. **For multi-role tables, write separate permissive policies per role and per operation (admin/tutor/student) combined with OR; use WITH CHECK on UPDATE (and INSERT) alongside USING so users cannot reassign rows; use a profiles/user_roles table (or app_metadata) as role source of truth, not raw_user_meta_data which users can self-edit.** — 
   - https://supabase.com/docs/guides/database/postgres/row-level-security
9. **Never call supabase with the service_role key from client code, and when using service_role server-side, add explicit ownership/role checks because it bypasses RLS entirely.** — 
   - https://www.permit.io/blog/supabase-authentication-and-authorization-in-nextjs-implementation-guide
10. **Do not enable ISR on any authenticated route or anywhere a session refresh can occur; apply the Cache-Control/Expires/Pragma headers from cookies.setAll, or set Cache-Control: private, no-store on auth routes, to avoid a cached Set-Cookie leaking one user's session to another.** — 
   - https://supabase.com/docs/guides/auth/server-side/advanced-guide

### Pitfalls

- Trusting supabase.auth.getSession() in server code for authorization — the cookie is forgeable; use getUser()/getClaims().
- Not returning the supabaseResponse from middleware (or not copying its cookies/cache headers onto a custom response) — refreshed tokens are dropped and users get randomly signed out.
- Enabling RLS but leaving a policy as USING (true) for authenticated — any logged-in user can read everything.
- Omitting WITH CHECK on UPDATE/INSERT policies — lets a user reassign a row's owner/user_id to someone else.
- Using the service_role key in a server action without re-checking ownership/role — service role turns RLS off.
- Relying on client-side route guards or middleware as the only gate — server actions are reachable via direct POST, so auth+role must be checked inside each action/handler.
- Storing roles in raw_user_meta_data (user-editable) instead of a profiles/user_roles table or app_metadata/JWT claims.
- Enabling ISR/caching on authenticated routes — a cached Set-Cookie can leak another user's session.
- Using the deprecated auth.role() in policies instead of the TO clause.

### Recommendation

Adopt the standard three-client pattern: lib/supabase/client.ts (createBrowserClient, singleton) and lib/supabase/server.ts (createServerClient with next/headers cookies(), new client per request), plus middleware.ts (Next.js 15) that calls getClaims()/getUser() to refresh the token and returns the supabaseResponse with its cookies. Do data fetching in Server Components, mutations in Server Actions (Zod-validated, typed return, revalidatePath after write), and Route Handlers only for external callbacks. Use getUser() (not getSession()) as the auth check in every Server Action, Route Handler and protected page/layout. Encode the admin/tutor/student rules as PostgreSQL RLS policies — this is the real security boundary — with per-role per-operation policies, WITH CHECK on writes, and role stored in a profiles/user_roles table (not raw_user_meta_data); then add per-role route/layout guards only as UX on top. Keep service_role server-only and add explicit checks where it is used. Disable ISR/caching on auth routes and propagate the cache headers from setAll to avoid session leakage.

## Idempotent earnings / ledger computation (tutor paid per approved lesson)

**Summary:** The safe way to pay a tutor "tutor rate x lesson hours" exactly once per approved lesson is to make the earnings computation a database-enforced idempotent write, not an application check. Two mechanisms combine: (1) an append-only earning-rows table with a UNIQUE constraint on the natural key (logbook_id, lesson_id) inserted via `INSERT ... ON CONFLICT DO NOTHING`, and (2) computing+inserting those rows inside the same transaction/RPC that flips the logbook status, gated by `UPDATE ... RETURNING` so an already-approved logbook yields zero rows and inserts nothing. Re-approval then cannot double-pay because either the status-guard short-circuits or the unique index swallows the duplicate. Amounts must be computed server-side in SQL (never from client input), stored as exact integer rupiah (or numeric), never float. Preview is just the same SELECT expression run read-only before approval, so the previewed total equals the persisted total by construction.

### Best practices

1. **Create a `tutor_earnings` (earning rows) table with a UNIQUE constraint on `(logbook_id, lesson_id)` and insert with `INSERT ... ON CONFLICT (logbook_id, lesson_id) DO NOTHING`. The natural key is the idempotency key; a retry can only insert rows that don't already exist, so repeated approvals add missing lessons but never duplicate a payment.** — A read-then-write check (SELECT for existing earnings, then INSERT) races under concurrency and double-pays. The unique index + ON CONFLICT makes dedup a single atomic write.
   - https://supabase.com/docs/reference/dart/upsert
2. **Create the uniqueness guarantee as a `CREATE UNIQUE INDEX` on `(logbook_id, lesson_id)`, not only an `ALTER TABLE ... ADD CONSTRAINT`, when you plan to use PostgREST/Supabase `.upsert()` or `ON CONFLICT` inference.** — Supabase users report error 23505 when ON CONFLICT inference fails against a constraint added via ALTER TABLE; Postgres ON CONFLICT prefers an index, and PostgREST passes column names, not constraint names.
   - https://github.com/orgs/supabase/discussions/28927
3. **Do the status change and the earnings insert in ONE transaction, using a CTE: `WITH approved AS (UPDATE logbooks SET status='approved' WHERE id=$1 AND status<>'approved' RETURNING ...) INSERT INTO tutor_earnings ... SELECT ... FROM approved JOIN logbook_lessons ... ON CONFLICT DO NOTHING`. If the logbook is already approved, the UPDATE affects 0 rows, the CTE returns nothing, and no earnings are inserted.** — This is the canonical 'conditional insert after an update' pattern: the two writes commit or roll back together, and the status guard makes re-approval a no-op before the insert is even reached.
   - https://stackoverflow.com/questions/62979036/conditional-insert-after-an-update-in-a-transaction
4. **Wrap the whole approve flow in a `SECURITY DEFINER` Postgres function exposed as a Supabase RPC, with `SET search_path = ''` (or `= public`), and validate the caller (`auth.uid()`, admin role) inside the function body. Revoke EXECUTE from anon/public and grant only to authenticated.** — The RPC is the atomic unit that can bypass RLS on the earnings table and enforce the invariant server-side. Supabase officially warns that a security-definer function without a locked search_path is a privilege-escalation path.
   - https://supabase.com/docs/guides/observability/advisors?lint=0009_duplicate_index
5. **Compute the amount in SQL from stored rate and hours (`round(tutor_rate_per_hour * hours)`), and derive any balance by summing earnings rows; never store a mutable `total_earned` that you increment.** — Client-supplied amounts can be forged; append-only rows replayed to a sum is the ledger standard (balances are derived, never stored as a mutable total that can drift or be double-incremented).
   - https://dodopayments.com/blogs/payment-ledger-design
6. **Store money as exact types: rupiah amounts as `bigint` (or `numeric(12,0)`) and hours as `numeric(5,2)`; never `float`/`double precision`. IDR has no fractional subunit in practice, so whole-rupiah integer is fine; keep a currency column if multi-currency is ever possible.** — Floats drift (0.1 + 0.2 = 0.30000000000000004); Postgres `numeric`/integer is exact. Integer minor units are the default recommendation for currency.
   - https://www.prisma.io/docs/orm/data-modeling/money
7. **Provide a preview as a plain read-only SELECT that uses the SAME expression and JOINs the approve RPC uses (logbook lessons x class tutor rate), so the shown total and the persisted total are one source of truth.** — Preview-before-approval should not duplicate the math in application code where it can drift from the stored result; share the expression (e.g., a SQL view or the same function) between preview and write.
   - https://www.crunchydata.com/developers/playground/working-with-money-in-postgres
8. **Treat the earnings rows as immutable/append-only. If a logbook must change after approval (add a lesson, correct hours), re-approve inserts only the missing rows via ON CONFLICT DO NOTHING; for a decrease/correction, post a reversing/compensating earning row rather than mutating or deleting the original.** — Mutating posted financial rows destroys auditability; compensating entries preserve a complete history, matching ledger best practice (never edit posted entries, post reversals).
   - https://www.moderntreasury.com/journal/how-to-scale-a-ledger-part-iii

### Pitfalls

- Storing money or hours as float/double — produces rounding drift; use bigint rupiah + numeric hours.
- Trusting a client-supplied amount or 'computed' total on approve — always recompute in SQL from rate x hours.
- Read-then-write idempotency (SELECT for existing rows, then INSERT) — races under concurrent approval and double-pays; use ON CONFLICT DO NOTHING on a unique index.
- Using ALTER TABLE ADD CONSTRAINT only, then relying on Supabase .upsert/ON CONFLICT inference — can throw 23505; create a CREATE UNIQUE INDEX instead.
- Allowing re-approval to UPDATE an already-approved logbook's hours after earnings were inserted — silently changes the basis of a posted amount; lock the logbook or post a reversal.
- Incrementing a mutable total_earned balance column instead of deriving the sum from append-only earnings rows — drifts and can be double-incremented.
- SECURITY DEFINER function without a locked search_path — Supabase flags this as a privilege-escalation path.
- Not gating the earnings insert on the approval state transition (UPDATE ... RETURNING), so an edit unrelated to approval could re-trigger payments — tie the insert strictly to the status flip.

### Recommendation

Concrete schema + approval transaction for the requirement (IDR, whole-rupiah amounts, hours can be fractional):

Tables (relevant subset):
- `logbooks(id uuid pk, class_id, tutor_id, period, status text check in ('draft','submitted','approved'), approved_at timestamptz, ...)`
- `logbook_lessons(id uuid pk, logbook_id fk -> logbooks, lesson_id, hours numeric(5,2))` — a lesson belongs to one monthly logbook.
- `classes(id uuid pk, tutor_rate_per_hour bigint)` — rate in whole IDR per hour.
- `tutor_earnings(id uuid pk, tutor_id, class_id, logbook_id, lesson_id, hours numeric(5,2), rate_per_hour bigint, amount bigint, created_at timestamptz default now(), UNIQUE(logbook_id, lesson_id))` — append-only, immutable. Back the uniqueness with `CREATE UNIQUE INDEX tutor_earnings_logbook_lesson_uidx ON tutor_earnings (logbook_id, lesson_id)` so PostgREST/ON CONFLICT inference works.

Approval RPC (one atomic transaction; caller must be admin, validated inside):
```sql
create or replace function approve_logbook(p_logbook_id uuid)
returns bigint   -- amount inserted, for confirmation
language sql
security definer
set search_path = public
as $$
  with approved as (
    update logbooks
       set status = 'approved', approved_at = now()
     where id = p_logbook_id
       and status <> 'approved'          -- idempotent gate #1
       and exists (select 1 from public.user_roles
                   where user_id = auth.uid() and role = 'admin')  -- admin-only
    returning id, class_id, tutor_id
  ),
  computed as (
    select a.id as logbook_id, a.class_id, a.tutor_id,
           ll.lesson_id, ll.hours,
           c.tutor_rate_per_hour,
           round(c.tutor_rate_per_hour::numeric * ll.hours)::bigint as amount
      from approved a
      join public.logbook_lessons ll on ll.logbook_id = a.id
      join public.classes c        on c.id = a.class_id
  )
  insert into public.tutor_earnings
        (tutor_id, class_id, logbook_id, lesson_id, hours, rate_per_hour, amount)
  select tutor_id, class_id, logbook_id, lesson_id, hours, tutor_rate_per_hour, amount
    from computed
  on conflict (logbook_id, lesson_id) do nothing  -- idempotent gate #2
  returning amount;
$$;
```
Why this is double-pay-proof: if the logbook is already approved, the UPDATE matches 0 rows, `approved` is empty, nothing is inserted (gate #1). If any race still slips through, the `UNIQUE(logbook_id, lesson_id)` + ON CONFLICT DO NOTHING makes the insert a no-op (gate #2). Re-approving after adding a new lesson inserts only that missing row.

Preview (read-only, same math — one source of truth): reuse the `computed` CTE as a plain SELECT (or a SQL view `logbook_earnings_preview`) so the UI preview total equals what the RPC will persist. The application never sends an amount; it only sends `logbook_id`.

Access: revoke EXECUTE from public/anon; RLS on `tutor_earnings` can be open to the tutor (see own rows) and admin, since all writes flow through the RPC. Earnings balance = `select sum(amount) from tutor_earnings where tutor_id = $1` — never a stored total.

## student-package-hours-balance

**Summary:** Model the purchased lesson-hour package as an immutable enrollment row holding total minutes, and derive "hours left" from an append-only usage ledger keyed by (occurrence, student). Store all durations as integer minutes (90-min lesson = 90, not 1.5) and all IDR as integer rupiah (bigint, no decimals). Deduct on the attendance/approval state transition, not the scheduled occurrence, and make each deduction idempotent with a unique constraint. Never store or mutate a "remaining" float/decimal; compute remaining as total − SUM(consumed).

### Best practices

1. **Store lesson durations and package totals as integer minutes, never as decimal hours or float; 90 minutes stays 90, and display '1.5h'/'1:30' only at the UI layer.** — Decimal hours are ambiguous and error-prone (1.30 vs 1.50), and floats accumulate rounding error. Minutes are discrete, so an integer column is exact and supports every display format.
   - https://stackoverflow.com/questions/41925298/what-data-type-should-i-use-for-a-duration-attribute
2. **Model the purchase as one immutable package/enrollment row holding total minutes (and paid IDR), and record every consumption as an append-only ledger row; compute remaining = total − SUM(consumed) instead of storing a mutable 'remaining' column.** — A mutable balance column destroys history ('balance amnesia'), drifts from the log, and races under concurrent writes. The ledger is the source of truth and the balance is recomputable for audit/reconciliation.
   - https://www.formance.com/blog/engineering/double-entry-accounting-for-engineers-building-financial-products
3. **Make each deduction idempotent with a unique key of (lesson_occurrence_id, student_id) on the usage ledger, and insert with ON CONFLICT DO NOTHING.** — Retries or double-clicked approval cannot charge the same student twice for the same lesson, regardless of how many times the action is replayed.
   - https://cloud.tencent.com.cn/developer/article/2744432
4. **Deduct hours on the attendance/approval state transition (the logbook approval), not when the lesson is scheduled; record leave/no-show as a zero or reversal entry rather than deleting the row.** — Charging on the scheduled occurrence would bill no-shows. Charging on attendance keeps booking and consumption as separate records, and reversals stay audit-complete.
   - https://twoqmllc.com/articles/tutoring-session-attendance-makeup-credits
5. **Store all money as integer rupiah in a bigint column (IDR has no fractional minor unit), and keep it as an integer/string in TypeScript; format only for display.** — Integer arithmetic is exact and avoids IEEE-754 rounding (e.g. 0.01 summed in double gives 9.999...). IDR has 0 decimal places, so bigint rupiah is sufficient and simpler than numeric(p,s).
   - https://docs.prisma.io/docs/orm/data-modeling/money
6. **Enforce no-overspend inside the same transaction as the ledger insert by checking SUM(consumed) + new_minutes <= total_minutes against the enrollment, so the deduction is all-or-nothing.** — A check-then-update in application code is race-prone; the balance guard must live in the same transaction as the write (conditional update or serializable isolation) so concurrent bookings cannot overspend a package.
   - https://dev.to/devaaai/handling-balances-and-transactions-patterns-and-anti-patterns-2lg

### Pitfalls

- Storing hours as float/double or decimal-hours (1.5) and summing them — rounding drift, and 1.30 vs 1.50 ambiguity.
- Keeping a mutable 'remaining_hours' column and decrementing it — loses history, drifts from the ledger, and races under concurrent deduction.
- Deducting at booking/schedule time instead of the attendance/approval event — charges students for lessons they did not attend.
- No unique constraint on (occurrence_id, student_id) — retries or double approval deduct twice.
- Storing IDR in float or in a currency-agnostic decimal column — rounding errors and lost precision in sums.
- Deleting a deduction row to 'refund' a no-show instead of appending a reversal — destroys the audit trail and risks double-refund.
- Using the locale-dependent Postgres money type — dump/restore across locales can corrupt amounts.

### Recommendation

Adopt a three-table model with integer minutes and integer rupiah, and compute the balance.

1. class_packages (the purchase/enrollment row): id, class_id, student_id, total_minutes int NOT NULL CHECK (total_minutes > 0), paid_amount_rp bigint NOT NULL, purchased_at timestamptz NOT NULL DEFAULT now(). One row per student-class purchase. total_minutes is immutable after purchase (600 minutes for a nominal '10-hour' package). Include a unique constraint on (class_id, student_id) if re-enrollment is disallowed, or allow multiple rows and sum for renewals.

2. lesson_occurrences (the scheduled lesson, shared source of truth for both consumption and tutor pay): id, class_id, starts_at timestamptz NOT NULL (WIB), duration_minutes int NOT NULL (90 for a 90-minute lesson), status (e.g. 'scheduled' | 'approved' | 'cancelled').

3. lesson_usage (append-only consumption ledger): id, enrollment_id FK, occurrence_id FK, student_id, minutes_consumed int NOT NULL, created_at timestamptz DEFAULT now(), with UNIQUE (occurrence_id, student_id). This is the only place hours are consumed.

Hours left for a student in a class = class_packages.total_minutes − COALESCE(SUM(lesson_usage.minutes_consumed), 0), grouped by enrollment; display hours as minutes/60 in the UI only. Do not store a remaining column.

Deduction flow: when an admin approves the tutor's monthly logbook (or marks a lesson occurrence as taught), insert one lesson_usage row per enrolled student inside a transaction that (a) checks SUM(existing) + duration_minutes <= total_minutes, (b) inserts with ON CONFLICT (occurrence_id, student_id) DO NOTHING for idempotency. The same approved occurrence is also what makes tutor earnings computable once — so one 'approved lesson' idempotently drives both student consumption and tutor pay from the same lesson_occurrences row. For a 90-minute lesson, minutes_consumed = 90; a 4-hour (240-minute) package then shows 2.5h remaining after one lesson.

Money: all rupiah values (student_rate per hour, tutor_rate per lesson, paid_amount) as bigint integer rupiah, formatted with Intl.NumberFormat('id-ID', { style: 'currency', currency: 'IDR', minimumFractionDigits: 0 }) at the display edge. No float, no numeric(p,s), no money type.
